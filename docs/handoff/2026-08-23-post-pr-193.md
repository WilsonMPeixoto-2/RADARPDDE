## 2. Por que existiram os PRs #190 a #193

A sequência não representa quatro reescritas independentes. Ela é uma linha causal de estabilização do mesmo fluxo operacional.

### PR #190 — latência crítica da avaliação mensal

Problema real observado por usuários: lançamentos Sim/Não/N/A podiam levar aproximadamente 10–20 segundos.

A RPC principal era rápida; o gargalo vinha de carregamentos remotos amplos feitos pelo DataService antes/depois da persistência, especialmente em entidades de auditoria volumosas.

O PR introduziu o uso de retorno remoto autoritativo para evitar leituras redundantes quando o resultado da própria operação já continha o estado necessário.

Não alterou regra de negócio, RLS, schema ou formato de auditoria.

### PR #191 — generalização da fluidez operacional

A correção foi generalizada de maneira controlada para outras escritas operacionais.

Contratos importantes consolidados:

- `remoteResultIsAuthoritative` quando o retorno da operação é suficiente;
- `remoteCommitIsAuthoritative` quando o commit remoto basta para preservar o contrato;
- `remoteRefreshExemptEntities` somente para entidades cuja dispensa de refresh é segura;
- `administrativeLogs` permanece a única entidade autorizada para a isenção ampla prevista nessa política;
- entidades mutáveis de negócio continuam conservadoras quando necessário.

O mesmo PR corrigiu, separadamente, um defeito real de integridade da transição de bens/NF por migration.

Migration relevante:

```text
20260822040642_invoice_asset_transition_integrity
```

### PR #192 — correção de segunda ordem após auditoria externa

A auditoria externa ajudou a identificar uma incoerência restante: embora as leituras remotas redundantes tivessem sido reduzidas, handlers do frontend ainda executavam `renderProntuario()` completo após escritas inline.

A decisão aceita foi eliminar o rerender integral no caminho normal de sucesso.

Contrato vigente desde então:

```text
persistência autoritativa
→ incorporação incremental do estado
→ reconciliação apenas do contexto afetado
```

`renderProntuario()` integral fica reservado a bootstrap, navegação, erro, retorno incompleto ou inconsistência não reconciliável.

### PR #193 — estabilização antes do uso real

O PR #193 consolidou a integridade funcional e a equivalência entre regra, banco, retorno autoritativo e UI incremental.

Foi implementado por TDD, sem escritas destrutivas de teste em Production.

As correções abrangem idempotência, transições condicionais, Assessoria por NF, pendências vinculadas, datas de disponibilização e reconciliação localizada.

## 4. Regras funcionais consolidadas no PR #193

### Resultado de bonificação

Campo `bonus_result` ausente significa preservar o valor existente. Campo explicitamente enviado vazio significa limpar a consolidação quando o contrato da operação exigir isso.

### Idempotência

Operação semanticamente idêntica ao estado atual não deve gerar nova persistência, novo `row_version` nem novo log apenas porque o usuário repetiu a mesma ação.

### N/A → Sim/Não

Ao sair de `N/A` para `Sim` ou `Não`, derivações incompatíveis com o estado anterior são reinicializadas. Para Nota Fiscal, a análise técnica volta a `Não analisado` quando aplicável.

### Assessoria de NF de serviço

A análise é individual por Nota Fiscal.

`Assessoria = Incorreto` exige pendência correspondente e a operação é atômica: a confirmação persiste NF, estado agregado, pendência e auditoria de forma coerente; cancelar o modal não pode deixar `Incorreto` persistido sem a pendência exigida.

Cada pendência de Assessoria identifica a NF de origem por `registered_invoice_id`.

NFs distintas podem ter pendências de Assessoria ativas simultaneamente no mesmo programa/competência. A mesma NF não pode duplicar pendência ativa equivalente.

A reanálise atualiza apenas a NF vinculada e depois recalcula o agregado mensal.

Depois que uma NF possui histórico de pendência de Assessoria vinculada, sua identidade estrutural necessária à rastreabilidade não pode ser silenciosamente trocada: escola, competência, programa e natureza da despesa ficam protegidos pelas regras correspondentes. Campos não estruturais permanecem corrigíveis conforme os contratos existentes.

### Datas do envio corretivo

`pendency_attempts.available_at` registra quando a escola disponibilizou o documento.

`pendency_attempts.submitted_at` registra quando o lançamento entrou no RADAR.

São conceitos distintos e devem sobreviver à ida e volta Supabase → estado legado → domínio.

### Reabertura

Conforme PEND-05, pendências `Resolvida` e `Cancelada` podem retornar a `Aberta` quando a operação de reabertura for válida, preservando histórico e auditoria.

### Dimensões independentes

Resultado de bonificação, situação da análise técnica, existência/estado de pendência e próxima ação operacional continuam dimensões independentes. Regularização posterior não reescreve automaticamente o resultado histórico da bonificação.

## 5. Arquitetura de escrita vigente

O caminho normal de sucesso é incremental:

```text
interação do usuário
→ feedback visual imediato
→ RPC/persistência
→ retorno autoritativo
→ aplicação no estado local
→ reconciliador escola + competência + programa
→ estabilização visual
```

Não voltar a executar `renderProntuario()` completo após toda escrita apenas “por segurança”. Esse padrão foi justamente uma das causas da sensação de lentidão corrigida pelos PRs #190–#192.

O fallback integral continua válido para erro, retorno incompleto ou estado que não possa ser reconciliado com segurança.

## 7. Ferramentas incorporadas na estabilização

### fast-check

Já está integrado como `devDependency` e usado em testes de propriedades/invariantes. Não é dependência de runtime.

Gate dedicado:

```bash
npm run test:properties
```

### MSW

Já está integrado como `devDependency` para cenários controlados de erro, latência, timeout, conflito e retorno remoto incompleto.

Gate dedicado:

```bash
npm run test:network-failures
```

### dependency-cruiser

Já está integrado ao gate arquitetural e também ao readiness.

```bash
npm run check:architecture
```

### Performance API / diagnóstico operacional

A base `operational-write-diagnostics.js` foi criada no PR #193, mas ainda não estava ligada ao runtime real no momento do merge.

O PR #194 completa essa integração sem telemetria externa:

- probe única e limitada em memória;
- fases `click`, `feedback`, `rpcStart`, `rpcEnd`, `applyStart`, `applyEnd`, `stable`;
- p50/p95 para feedback, RPC, aplicação local e clique→estável;
- Performance API nativa quando disponível;
- `PerformanceObserver` usado apenas para consumo/limpeza local das medidas quando suportado;
- interface de consulta somente leitura `window.RadarOperationalWriteMetrics.snapshot()` e `.summary()`;
- nenhuma métrica enviada para Supabase, Vercel ou terceiros;
- nenhuma persistência em LocalStorage/IndexedDB;
- nenhuma escola, usuário, competência, programa, NF, pendência, UUID de entidade ou texto de negócio coletado;
- falha da instrumentação é fail-open e não bloqueia a operação funcional.

## 9. Vulnerabilidades conhecidas de dependências

No checkpoint de 23/08, `npm audit` continua apontando duas vulnerabilidades moderadas na cadeia ExcelJS/UUID.

A decisão vigente é **aceitar conscientemente o risco atual e acompanhar futuras versões compatíveis**.

Não executar nesta frente:

```text
npm audit fix --force
atualização rompendo ExcelJS apenas para zerar o audit
substituição oportunista de biblioteca
mudança de versão sem validação funcional do Excel
```

O gate atual bloqueia vulnerabilidades de severidade `high` ou superior. As moderadas conhecidas permanecem visíveis e monitoradas.

Esta decisão não significa ignorar segurança. Significa não trocar uma vulnerabilidade moderada transitiva por uma quebra funcional deliberada. Reavaliar quando houver correção compatível, mudança de exposição ou elevação de severidade/risco.

## 12. Quando reabrir uma decisão consolidada

Uma decisão já encerrada só deve voltar à mesa por evidência material, como:

- defeito reproduzível;
- dado real inconsistente;
- exigência institucional/negocial nova;
- vulnerabilidade ou risco de segurança materialmente alterado;
- incompatibilidade comprovada no código ou banco;
- decisão explícita de produto.

Não reabrir porque outra ferramenta prefere outra arquitetura, porque existe um pacote mais moderno ou porque uma auditoria antiga descreveu um estado anterior.
